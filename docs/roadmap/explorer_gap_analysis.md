# Explorer vs. Torii Capability Matrix

This is the current first-release contract map for the Explorer and the sibling `../iroha` checkout. Historical
pre-release `/v2`, backend-proxy, anonymous diagnostic, and compatibility designs are not requirements.

The installable SDK/Mochi baseline is pinned exactly in `package.json`, `pnpm-lock.yaml`, and
`tests/mochi/explorer-profile.json`. Any later sibling commit must be published and then repinned on all three surfaces
before it can become a reproducible Explorer dependency.

## Closed pre-release gaps

- The frontend talks directly to Torii V1 and the browser-safe Iroha SDK; there is no `/api` or `/v2` compatibility
  layer.
- World lists use the current cursor contract. Transactions and instructions additionally bind history to an immutable
  snapshot. The Explorer does not synthesize numbered pages.
- Resource-detail selectors are canonicalized before transport and their returned identities are checked against the
  request. A valid DTO for a different account, asset, definition, domain, NFT, RWA, block, transaction, instruction,
  dataspace summary, SoraFS manifest, proof, or verifying key is rejected rather than displayed.
- System parameters, confidential-asset policy, Soracles feed history, and latest DeFi attestations consume their signed
  current DTOs directly; unknown fields and response-identity mismatches are terminal contract errors.
- Instruction presentation consumes the required Norito evidence fields and canonical structured payload. It does not
  accept `r#box`, missing evidence, alternate boxes, or first-key payload inference.
- Runtime config rejects unknown and retired public fields. Network identity is an exact checked `NetworkId`, never a
  human chain label.
- Root diagnostics and protected app endpoints are not browser data sources or failover candidates.

## Known upstream contract gaps

- Soracles `FeedId` still permits the valid names `.` and `..`, but the only history selector is a path segment that
  browsers normalize even when percent-encoded. EX-310 requires a path-safe registration rule or a non-path selector;
  the Explorer rejects these unaddressable identities instead of double-encoding or rewriting them.
- Soracles returns the complete feed registry with no feed-count cap and each complete retained history vector without a
  limit or continuation, while configured history retention is unbounded. EX-311 requires snapshot-bound cursor
  contracts and published limits. The Explorer accepts the exact responses and does not invent local caps that would
  reject valid Torii payloads.
- Successful Soracles entries are server-sorted by Rust `AccountId` order. The pinned browser SDK exposes canonical
  address bytes but not the equivalent controller comparator (especially for multisig policies), so the Explorer checks
  nonempty/unique/uniform-scale/inlier invariants without duplicating a subtly different ordering algorithm.

   route or DTO.
2. Correct the browser SDK asset-detail normalizer to consume Torii's authoritative `value` field (EX-302); keep the
   strict direct route until the repaired helper is contract-tested upstream.
3. When a later upstream SDK revision is published and signed, repin the SDK dependency, lockfile, and Mochi source
   profile together and rerun the exact-toolchain gate.
4. Resolve dot-segment Soracles feed addressing upstream (EX-310); do not add a browser-side encoding shim.
5. Add bounded snapshot-cursor pagination to Soracles collection reads upstream (EX-311), then expose cursor UI.
6. Keep this matrix synchronized with `../iroha` whenever a Torii route classification, DTO, or SDK method changes.
